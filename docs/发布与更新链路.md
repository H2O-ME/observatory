# 发布与更新链路（0.3.7 起：CI 直推部署）

> 本文是 **代码发布 / 生产部署 / 受控端安装包上线** 的唯一操作说明。
> 0.3.7 起部署由 GitHub Actions 直推服务器；轮询式自动更新（auto-update.timer）
> 已拆除——它无法感知发布意图、会被 systemd 超时打断在换容器中途
> （2026-10-26 八小时宕机的直接原因，见 §8）。

## 1. 拓扑

```
本地开发机
  │  tools/release.sh            （唯一发布入口：bump → commit → tag → push）
  ▼
GitHub 仓库
  ├─ main  ──► Actions 只跑质量门禁，不部署
  └─ v* tag ─► Actions:
        门禁 version/lint/server/contract/acceptance/webui/deploy-static/nginx
          ▼
        agent-windows（Windows runner 构建受控端 zip）
          ├─ 强推 agent-dist 分支
          ├─ 建 GitHub Release（zip + SHA256SUMS）
          ▼
        deploy job（最后一个 job，等 agent-windows 完成）
          ├─ SSH（受限密钥 → ci-gate.sh）点火 deploy.sh release v*
          ├─ 轮询 deploy.status 直到 success/failed
          └─ 红灯 = 部署失败（服务器已自动回滚）
                ▼
部署服务器（/opt/observatory）
  deploy/deploy.sh worker（setsid 脱离会话，SSH 断线不影响）
  ├─ fetch tag → 快备份（DB+证书秒级）→ build 新镜像（旧容器不受影响）
  ├─ compose up 切容器 → 多点健康验证（见 §4）→ 任一不过自动回滚
  ├─ fetch-agent-package.sh 登记 agent-dist（校验 sha256）
  ▼
在线受控端下一次心跳拿到 update_offer → 自行升级（SYSTEM，无 UAC）
```

服务器**不保存 GitHub PAT**；git 拉取用只读 deploy key（`~/.ssh/id_ed25519_observatory`，
`origin` 指向 SSH alias `github-observatory`）。CI 部署走一把独立的
**受限 SSH 密钥**（`authorized_keys` 里 `command="/opt/observatory/deploy/ci-gate.sh"`
强制命令封装，只能执行 `release vX.Y.Z` / `status` / `logs`）。

## 2. 发布（一条命令）

```bash
tools/release.sh              # patch +1（默认）
tools/release.sh minor        # minor +1
tools/release.sh 0.4.0        # 显式版本
tools/release.sh patch -m "修复xxx"
tools/release.sh patch --no-watch   # 推完就返回，不等 CI/部署
```

脚本做的事：干净树/主分支/与远端同步预检 → `set_version.py` bump + `--check` →
提交 `chore(release): vX.Y.Z` → 打 tag → 用 PAT 推送 main+tag → 盯 CI run
（一个 run 的 conclusion 覆盖所有 job，含 deploy）→ 终验生产 health。

- PAT 来源：环境变量 `SHENMI_GITHUB_TOKEN` 或 `.localdata/github-token`
  （已 gitignore）。需 `repo` + `workflow` scope（碰过 workflow 文件的提交历史要求）。
- `main` 上普通 push：只跑测试，**绝不部署**。部署只由 tag 触发——这是刻意设计：
  半成品 main 永远不会再被自动拉上生产。

## 3. Actions 的 deploy job

触发条件：`refs/tags/v*`；依赖全部质量门禁 + agent-windows（受控端包必须与服务端
同版本一起发布）。流程：

1. 把 secret `OBS_DEPLOY_KEY` 写入临时密钥文件；
2. `ssh … "release vX.Y.Z"` 点火（deploy.sh 的 supervisor 立即返回）；
3. 每 15s `ssh … status` 轮询状态文件，最长 35 分钟；
4. `result=failed` 时拉取服务器日志尾部，job 红灯；
5. 无论成败，在 job summary 里贴最终状态。

Secrets（仓库 Settings → Secrets → Actions）：

| 名称 | 值 |
| --- | --- |
| `OBS_DEPLOY_KEY` | CI 部署私钥（本地 `.localdata/obs-ci-deploy-key`，公钥装在服务器） |
| `OBS_DEPLOY_HOST` | `<server-ip>` |
| `OBS_DEPLOY_PORT` | `2009` |
| `OBS_DEPLOY_USER` | `root` |

## 4. 服务器侧 deploy.sh

```
deploy.sh release <vX.Y.Z> [--full-backup]   # 异步点火（supervisor，立即返回）
deploy.sh status                             # 状态文件（CI 唯一事实来源）
deploy.sh logs [N]                           # 尾随最近一次部署日志
deploy.sh rollback                           # 人工回滚到上一版本（用状态文件记录）
deploy.sh reset-breaker                      # 清除熔断计数
```

worker（脱离会话）的关键保障，全部来自实战教训：

- **supervisor/worker 分离**：触发方掉线/被杀不影响部署；worker 由 setsid 启动。
- **多点健康验证**（任一不过自动回滚）：
  1. 容器内回环 health（绕过一切网络位形，验证应用本体）；
  2. 宿主用真实 `Host: <console>` curl（模拟 nginx 反代路径，**会过 HostSplit**——
     只测回环的旧方式漏掉了策略层回归）；
  3. docker healthcheck 达 `healthy`；
  4. 版本端点 == 目标版本；
  5. `/data/webui/.version` == 目标版本（前端不是旧 SPA）。
- **快备份**：默认 DB 在线快照 + 证书 + `.env`（秒级）；数据卷全量 tar 只在
  `--full-backup` 时执行（帧数据另有 GitHub 增量归档兜底）。
- **幂等**：目标 commit / 运行版本 / WebUI 版本齐备 → no-op，重复触发不重建容器。
- **熔断**：同一 commit 连续 3 次失败后拒绝自动部署，`reset-breaker` 解除。
- **脚本自升级**：worker 检出 tag 后 re-exec 该版本自带的 deploy.sh——脚本修复随
  下一个 tag 生效。

## 5. 手工兜底

```bash
ssh root@<server-ip> -p 2009 -i <管理密钥>
cd /opt/observatory

bash deploy/deploy.sh release v0.3.7   # 手动部署某个 tag（与 CI 同路径）
bash deploy/deploy.sh status           # 看状态
bash deploy/update.sh                  # 已废弃入口的 shim：部署 origin/main 的 VERSION 对应 tag
```

## 6. 发布验证

```bash
curl -fsSk https://control.tianhw.top/api/v1/health   # ok:true 且 version 正确
docker ps --format '{{.Names}} {{.Image}} {{.Status}}' | grep observatory
docker exec observatory-api cat /data/webui/.version
```

Actions 的 deploy job 绿灯 + 上面三条正常 = 发布完成。

## 7. 凭据与安全

- 服务器 git deploy key **只读**；CI 部署密钥**强制命令**（ci-gate.sh 白名单），
  两把钥匙互不重叠；本机管理密钥仍是完整 root。
- PAT 只存本机 `.localdata/github-token`（gitignored），不进 remote/env/日志；
  泄露过历史的令牌应作废轮换。
- ci-gate.sh 会严格校验 `vX.Y.Z` 形态；deploy.sh 对 tag 再校验一次（双保险）。

## 8. 2026-10-26 宕机复盘（为什么旧链路必须死）

1. timer 在无发布意图时拉走 main 全量重建容器（同版本也重建）；
2. 新上线的 HostSplit 中间件要求 `Host:127.0.0.1` 的请求来自 loopback 客户端，
   而 update.sh 的健康检查从宿主 curl，客户端是 docker 网桥 IP → 永远 403 →
   健康检查永远失败 → 回滚循环；
3. 第二轮重试的回滚被 systemd 超时 SIGKILL 打断在「旧容器已改名、未 start」的
   中间态——新旧容器两头落空，生产宕机 8 小时无人发现。

对策即本文件的新链路：tag 才部署、快备份、幂等 no-op、多点验证（含真实 Host
路径）、worker 脱离会话、失败自动回滚 + 熔断、CI 红灯可见。
