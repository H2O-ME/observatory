# 项目通读报告（Observatory 0.2.10）

> 本报告由 6 个并行阅读智能体 + Lead 交叉复核产出。分层原始报告（服务端 API / 服务端 services / 受控端 / 控制台 / 运维 / 跨层契约）各 400–800 行，含全量 `file:line` 取证，另行保存；本文是可执行结论的汇总。
> 复核方式：逐行阅读 + `grep` 取证 + `python -m compileall` + `python tools/test_server.py` 实跑。

---

## 1. 一句话结论

这是一套**工程素养明显高于同规模自研项目**的授权设备观测系统：三条核心设计（单一 presence、单一命令总线、诚实降级）在结构上确实落地了，代码注释普遍解释"为什么"而不是"是什么"，自检 222 项断言覆盖了版本/鉴权/双域名/总线/画面/更新/控制转发。

但它离"完成"还有距离，且**问题集中在两个地方**：一是**内核机制缺少闭环**（命令总线不留痕、归档半成品、实时控制的 TTL 只管画面不管输入），二是**边界与运维面**（受控端卸载/重启/强制更新的三条关键路径实际不可用或无校验，证书与升级链不可回滚，文档与代码漂移 14 处，README 还写着 0.2.0）。

**健康度实测**：`compileall` 全绿；`tools/test_server.py` **221/222 通过**，唯一失败项是废弃名称扫描命中了当次分析产生的临时文档（已清理，清理后即 222/222）——这条失败恰好证明了测试是真的在扫。

## 2. 系统全貌

```
┌────────────┐  HTTPS/WSS   ┌──────────────────────────┐
│ 控制台 WebUI│ ───────────▶ │ 控制服务器 (FastAPI)      │
│ React18+Vite│ ◀─────────── │ presence / bus / storage │
└────────────┘ server_time  └───────────┬──────────────┘
                                         │ HTTPS 长轮询 / WSS
                             ┌───────────▼──────────────┐
                             │ 受控端服务进程 (SYSTEM)     │
                             │ 传输阶梯 + 更新 + 卸载      │
                             └───────────┬──────────────┘
                                 命名管道 │ PeekNamedPipe 轮询
                             ┌───────────▼──────────────┐
                             │ 会话 worker (用户会话) × N  │
                             │ 采集 / SendInput / 文件    │
                             └──────────────────────────┘
```

| 层 | 位置 | 规模 | 技术 |
|---|---|---|---|
| 服务端 | `server/observatory/` | 约 5.2k 行 Python | FastAPI + SQLAlchemy async + SQLite + PyJWT/bcrypt/pyotp |
| 受控端 | `agent/observatory_agent/` | 约 4.6k 行 Python | pywin32 + mss + Pillow，PyInstaller **onedir** |
| 控制台 | `webui/src/` | 约 8k 行 TS/TSX | React 18 + zustand + React Query + shadcn(Base UI) |
| 部署 | `deploy/` | 11 脚本 + nginx | 单容器 + 宿主 nginx 双域名 + certbot |
| 工具 | `tools/` | 3 套测试 + 版本/体检 | 端到端自检、e2e、部署体检 |

运行时是**一个容器、一个进程、一个 app**：TLS 在这里终止，SQLite 在数据卷上，同一进程同时服务控制台 SPA、设备 API 和两个 WebSocket（`server/observatory/main.py:1-5`）。全局长生命周期对象集中在 `Runtime` 单例（`services/runtime.py:33-98`），避免了散落的模块级全局。

## 3. 服务端

### 3.1 装配与生命周期（`main.py:130-202`）

`create_app()` 顺序：`ensure_dirs → FastAPI(禁用 docs/openapi) → HostSplit 中间件 → 版本响应头中间件 → api_router(/api/v1) → /install.ps1 → /assets 静态(immutable) → / 与 SPA 回退`。

`lifespan`（`main.py:95-112`）：发布内置前端到数据卷（带 `.version` 标记防漂移）→ `Runtime.create` → 起 housekeeping 协程（每 20s：清理陈旧通道、过期命令；每 30 tick ≈10min：跑一次 retention）。

### 3.2 鉴权（四类凭证）

| 身份 | 凭证 | 校验点 |
|---|---|---|
| 控制台 | JWT HS256（`obs_session` Cookie 或 `Authorization: Bearer`） | `deps.require_admin`（`deps.py:63-69`），Cookie 存在的理由是让 `<img>` 吃到浏览器缓存 |
| 受控端 | `X-Device-Token`（32 字节随机，仅存 HMAC 摘要） | `deps.require_device`（`deps.py:78-93`）；WS 另从 header/query 取（`deps.ws_device_token`） |
| 注册 | 共享 `OBS_ENROLL_CODE` + 按 IP 限流 | `api/agent.py:40-104`，`hmac.compare_digest` 定时安全比较 |
| 双域名 | Host 白名单 | `hostsplit.py:62-137` |

### 3.3 双域名规则（`hostsplit.py`）

`console_host` 提供控制台；`agent_hosts` 提供安装脚本与设备接口；`/api/v1/agent/*`、`/api/v1/public/*`、`/health`、`/version`、`/install.ps1` 两域名共享。错配时：HTTP 404 + 中英文提示并指向控制台域名，WS 直接 4403 关闭。

但隔离是**配置退化即 fail-open**：`enabled` 要求两个列表都非空；未知 Host 一律当控制台；且优先信任客户端可控的 `X-Forwarded-Host`（`hostsplit.py:56-59`）。

### 3.4 数据与迁移

6 张表：`devices / frames / commands / audit / settings / packages`（`models.py:27-133`），时间戳一律 BIGINT 毫秒，**没有 datetime**。没有迁移框架：`db.py` 用 `create_all` + 手写"缺列则 ALTER"（`db.py:71-95`）——加索引进不了老库。

### 3.5 presence：唯一事实来源（`services/presence.py`）

这是整个系统的地基，也是最扎实的一块。

- 通道注册表 `ChannelRegistry` 在内存里记 `ws` / `poll` 两种通道（`presence.py:61-138`）。
- 四个硬编码窗口：`WS_STALE_MS=65s`、`POLL_STALE_MS=150s`、`OFFLINE_AFTER_MS=120s`、`CAPTURE_STALE_MS=180s`（`presence.py:29-37`）。
- 状态机：`online / degraded / offline / uninstalling / uninstalled`，每态都带**人话 reason**（"仅轮询通道，实时控制不可用"、"没有已登录的交互式桌面，无法采集屏幕"）。
- 关键设计：**HTTP 心跳永不降级活跃 WS**（`presence.py:81-90`），poll→ws 升级保留 `since_ms`，避免 UI 报告一次没发生过的断线。
- `capabilities` 按状态推导（`presence.py:141-174`）：`control` 需要实时通道，`files/screenshot/update` 走命令总线两通道都行。
- `merge_agent_report()`（`presence.py:177-208`）是两条传输路径（HTTP 心跳、WS 心跳）**共用**的落库函数——历史上正是这里漂移导致"WS 设备丢失采集健康"。

### 3.6 命令总线：一次下发只有一条路（`services/bus.py` + `services/commands.py`）

1. `create()` 先落库为 `pending`（`commands.py:120-164`），**再**尝试 WS 推送，推不到就 `notifier.notify_command` 唤醒长轮询。
2. 每个命令在 `CommandBus` 里有一个 `Waiter`（`bus.py:29-56`），谁先回答都汇合到 `settle()`，首答胜出（`bus.py:68-89`）。
3. 设备侧：WS 直推，或 HTTP `/agent/commands` 长轮询 `claim_pending`（`commands.py:186-203`）；结果从 `/agent/commands/{id}/result` 或 WS `{"t":"result"}` 回来，两条路都调 `record_result`。
4. 超时：默认 30s，`files` 90s、`update/uninstall` 60s（`commands.py:44-51`）；命令过期是 `timeout×3`（`commands.py:141`），由 housekeeping 的 `expire_stale` 收割。
5. 白名单：11 种命令 + 4 种需显式确认（`commands.py:25-42`），文件操作 12 个 op 在 `validate_payload` 里逐项校验。

### 3.7 画面链路与保留

`ingest.store_frame` → `storage` 落盘 → `transcode` 在线程池转 WebP（Semaphore(2) 限流，事件循环不被 190ms 编码卡住）→ 缩略图 → `timeline` 按桶聚合。收藏/保留/配额在 `retention.py`，可选归档在 `archive.py`（见 §7）。

## 4. 受控端（Windows）

### 4.1 进程模型

SCM → `service.py`（SYSTEM，负责生命周期、failure actions）→ `runner.py`（主循环：传输、配置、命令）→ `session_launch.py` 用 `WTSQueryUserToken → DuplicateTokenEx(TokenPrimary) → CreateEnvironmentBlock → CreateProcessAsUserW(winsta0\default)` 把 worker 拉进**用户会话**（`session_launch.py:151-190`）。

README 说"两进程"是简化：实际是 **1 个服务进程 + 每个可采集会话 1 个 worker（0..N）+ 临时 update/uninstall helper**。采集与注入必须发生在用户会话，更新与卸载必须在无登录时也能做——这是双进程架构的真正理由。

### 4.2 命名管道

与服务端共用 framing：`uint32 BE 头长 | JSON 头 | payload`（`pipe_proto.py`）。读端用 `PeekNamedPipe` 轮询而非阻塞 `ReadFile`，规避同步句柄死锁——这是踩过坑的写法，注释里写明了。请求/响应按 id 配对，采集帧走流式推送。

### 4.3 传输阶梯（`transport.py` + `runner.py`）

ws(0) → long-poll(1, 服务端 hold 25s) → short-poll(2, 每 5s)。失败即降级，重连退避 2–120s；轮询稳定在线后每 120s 起做指数向上探测（上限 1800s），探测成功就回到 WS。**只有 WS 承载实时控制**。

### 4.4 采集

`capture.py` 用 64×36 灰度网格指纹做主判定（比 dHash 便宜且支持忽略区域），无变化直接跳过缩放与编码；静止时采集间隔与强制帧间隔一起指数退避（封顶 60s/300s），有变化立刻回落。帧先在受控端 JPEG 编码，服务端再转 WebP（受控端做 WebP 是 JPEG 的 30 倍成本）。`spool.py` 负责落盘重传（上限 2000 条/48h）。

### 4.5 输入注入与文件

`input.py` 用 `SendInput`，坐标归一化到 0..10000。`fs_ops.py` 支持 12 种操作（list/stat/mkdir/delete/rename/copy/move/search/drives/read/write/hash），分片读写 ≥1 MiB。

### 4.6 更新与卸载

更新：下载 → **流式 sha256 校验** → 预检（新 exe 能否 `--version`）→ 由 helper 替换 → 失败回滚，全程无 UAC（`updater.py`）。卸载：服务自身以 SYSTEM 清理（`uninstall.py`）。

这两条在**自动路径上设计正确**，但手动/异常路径有硬伤，见 §7 P0-1/P0-3。

## 5. 控制台

- 路由（`App.tsx`）：login / wall / device（overview·files·live·timeline·commands）/ audit / settings / updates，守卫是"守卫式渲染"而非路由 wrapper。
- 数据获取：React Query 轮询 + WS 事件触发失效（无 SWR、无自研 fetch 层）；9 类查询各有间隔。
- 时钟：`store/live.ts` 里 `serverNow() = syncedServerMs + performance.now() 增量`，设计正确——但**只有 WS 事件在喂它**（`live-bridge.tsx:33`），REST 响应里的 `server_time_ms` 前端一个都没读。
- presence 消费：`lib/presence.ts` 只做**防御式归一化**（缺字段就降级，不崩），全仓 0 处 `isOnline` 自算在线。
- 视觉：shadcn base-nova + Base UI，业务零定制，定制全在 `index.css` 设计令牌层；为 Chromium 81 做了 legacy CSS/JS 降级插件。

## 7. 问题清单（跨 6 份报告去重，按严重度）

### P0 · 会导致功能失效 / 安全边界被绕过

1. **远程卸载是真坏的**（已实测复现）：`uninstall.py:42-48` 只把 `observatory-agent.exe` 复制到 `%TEMP%`，但产物是 PyInstaller **onedir**，单 exe 启动即报 `Failed to load Python DLL ..._internal\python314.dll`。更糟的是 `runner.py:718` 先 ack 服务端、`723-727` 不检查 spawn 结果、随后照常停服务 → 服务端显示"已卸载"、设备离线，**实际服务与文件都还在**。
2. **`restart_agent` 只停不启**（`runner.py:585-587,729-743`）：进程正常上报 STOPPED，SCM failure actions 不触发 → 远程"重启受控端"≈ 设备离线到下次开机。
3. **强制更新绕过完整性校验**：远程 `update` 命令只带 version 不带 sha256（`commands.py:89-92` → `runner.py:578-581,698` → `client.py:234` 空摘要直接跳过校验），且 `_forced` 跳过版本比较 → 可被投毒、可降级；全链无 Authenticode 签名。（自动更新路径反而是完整的：流式 sha256 + 预检 + 回滚。）
4. **`archive_token`（GitHub PAT，仓库写权限）下发给每一台受控端并落盘**：`effective()` 返回全量配置（`settings_store.py:176-187`），enroll/heartbeat/poll/WS welcome/pong 全裸发（`api/agent.py:85,96-104,138-142,179,277`、`api/agent_ws.py:83,101`），受控端 `apply_server_config` 整份存本地；`/devices` 的 `DeviceOut.settings` 也回给浏览器。只有 `GET /settings` 用了 `public_view()`。
5. **实时控制的 TTL/撤销只管画面不管输入**：`pump_input` 转发 `ctrl_in` 从不校验 grant（`control.py:154-173`）；`DELETE /control/{token}` 只内存 `pop`（`control.py:96-100`），既不关已建 WS 也不发 `ctrl_stop` → 输入可以一直注入。
6. **证书链路三处叠加缺陷**（`deploy/`）：`setup.sh:98-101` 把证书做成指向宿主 `/etc/letsencrypt` 的**绝对符号链接**，而 compose 只挂 `../certs`（`docker-compose.yml:28`）→ 容器内链接悬空，TLS 起不来；`renew-certs.sh:14` 续期仍用 `--standalone`，而 nginx 常驻 80 端口 → 90 天后续期失败且失败被吞、退出码 0；`setup.sh:86` 假设两个域名各有 live 目录，一次 certbot 双 `-d` 通常只有首域名。**（静态证据确凿，具体表现需上机 `ls -l /opt/observatory/certs` 确认。）**
7. **升级不可回滚**：`update.sh` 不备份 DB、镜像只有 `:latest`、`git pull --ff-only` 使脚本内回退不可能；健康检查失败只打印一行，而 `setup.sh` 健康检查失败后**仍打印"部署完成"**。

### P1 · 高概率故障或明确的契约违背

8. **客户端 20s 超时 vs 服务端 20/25/45/60s 等待**（`api.ts:85` vs `files.py:118,146,176,228`）：慢设备的大文件操作必然先报超时；安装包上传（唯一的自动更新入口）同样被 20s 卡死。
9. **命令总线 waiter 确定性泄漏**：`create()` 无条件 `bus.open()`（`commands.py:147`），只有 `wait_for()` 会 `forget()`（`commands.py:314`），`settle()` 不删 → 每条控制台命令/卸载命令永久留一个 Waiter（两个智能体各自脚本复现）。
10. **命令交付语义有洞**：WS 重连不 drain 离线期积压的 pending（`agent_ws.py:94-105`）；poll 路径先 commit `dispatched` 再返回（`commands.py:186-203`），响应丢失=命令永久丢；`push` 与 `claim` 之间有重复投递窗口。
11. **8443 默认绑 `0.0.0.0` + `trust_forwarded_for=true` + HostSplit fail-open**：绕过 nginx 直连时可伪造 Host 进控制台、伪造 `X-Forwarded-For` 绕登录限流并污染审计 IP；而 `docs/部署.md:11` 写的是"只监听回环"。
12. **归档子系统只落了一半**：`archive.py` 是逐帧 fire-and-forget 的 GitHub Contents API PUT，没有"打包→上传→校验→才删本地"；路径把 uid 拼两次（`archive.py:74`），删除只扫一层且只保留 `type=="file"` → `delete_device` 恒删 0 个文件；本地 retention 完全不等归档结果。也没有备份页/接口（`api/backup.py`、`pages/backup.tsx` 不存在）。
13. **capabilities 过度承诺**：`control` 不看 `control_enabled`（UI 放行、接口 403）、`update` 不看 `can_self_update`/是否有新包、`transport=none` 时 `files` 仍为 true（UI 说可用，实际等下一条心跳）。
14. **安慰剂配置项**：`ws_enabled`、`poll_interval_s`、`transport_reprobe_s`、`agent_offline_after_s`、`max_upload_bytes`、`frames_per_bucket` 定义了但无人消费；离线阈值硬编码 120s，而文档仍把它列为可调项。
15. **多显示器鼠标坐标必错**：`mouse_move` 用主屏尺寸归一化却带 `MOUSEEVENTF_VIRTUALDESK`（`input.py:106-129`），与"所有显示器拼合采集"不一致；全仓无 DPI 感知设置。
16. **跨进程安全**：命名管道用 NULL 安全属性、无客户端身份校验（`pipe_server.py:97-109`）→ 本机任意进程可冒充 worker 发帧/注入；401 失效 token 不会重新注册（`_reregister` 定义于 `runner.py:389-392` 但零调用）→ 阶梯降级后永久离线。
17. **安装器凭据**：控制台下载的 `.cmd` 明文内置共享注册码、无过期/一次性/设备绑定（`install.cmd:18`）；`/public/agent/latest` 等下载端点无需注册码。
18. **文档漂移 14 处**：README 版本仍写 **0.2.0**（实际 0.2.10）；`docs/部署.md` 的 8443/28 项体检/备份恢复口径均与实现不符；`docs/受控端打包.md` 指的工作流路径已迁移；`docs/合规与授权.md` 说保留 7/30 天，实际默认 14/180 天。
19. **测试门禁缺口**：CI 只跑 `test_server.py`；`test_agent.py` 与 `test_e2e_live.py` **从不进 CI**；而 README 称 e2e 是"唯一能证明界面没说谎的测试"，实际它是纯 HTTP 脚本，不碰浏览器。

## 8. 值得肯定的地方

- **注释写"为什么"**：几乎每个非显然决策都附历史原因（如"HTTP 心跳不许降级 WS——旧版正是因此谎报仅轮询"），这在自研项目里罕见。
- **单一事实来源真的做到了骨架级**：删掉 presence 会牵动 6 个 API，说明没有第二条路径。
- **零 TODO/FIXME/HACK**，零裸 `except:`，176 个受跟踪文件无构建产物，`.gitattributes` 锁死版本文件换行。
- **自检质量高**：222 项断言，连"仓库里不许出现废弃项目名"这种迁移纪律都有测试。
- **自动更新路径是完整的**：流式 sha256、预检、原子替换、失败回滚——可惜手动更新路径没复用这套纪律。
- **降级文案诚实**：不做"假装正常"，这是绝大多数同类系统做不到的。
